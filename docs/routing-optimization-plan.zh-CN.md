# Sub2API 调度站点与监控调度优化建议

> 历史规划归档（2026-09-20 标注）：正文保留此前阶段的建议，不代表当前全部功能状态。URL/Key 自动关联、SQLite 存储及自动推送/停调恢复现已实现；当前规则以 [当前项目全部功能与运行逻辑](project-functional-logic.zh-CN.md) 和 [自动推送说明](automatic-routing.zh-CN.md) 为准。

更新：2026-09-19。此版本替代此前多站关联方案。当前范围是 Sub2API 调度站点、上游供应商与监控站，运行方式见 [当前关联说明](site-relationships.zh-CN.md)。

## 1. 目标与边界

让调度站点在处理模型请求时，尽量选择可用、稳定、费用符合要求的上游账号。监控站负责提供精确到令牌和模型的判断，实际业务请求仍由 Sub2API 处理。

项目不再接入 NewAPI 主站的管理接口，不读取其分组售价或日志，不编辑其定价，也不要求建立跨站分组关系。第三方 NewAPI 上游仍保留普通用户接入能力。

监控站故障或重启时，调度站点应能继续按照自己的配置处理请求。自动控制不能成为每一次业务请求必须同步经过的额外服务。

## 2. 当前已经实现

| 能力 | 实际行为 |
| --- | --- |
| 调度站点接入 | Admin API Key 读取全部分组、账号及所属分组 |
| 上游目录 | 普通用户身份读取余额、可访问线路及已创建令牌 |
| 模型探测 | 各令牌分别拉取模型；符合执行条件的各模型每分钟探测 |
| 结果整理 | 按类别和模型组织，时间轴精确到令牌，异常折叠并保留重新验证 |
| 账号关联 | 保存调度站点账号 → 上游令牌 → 模型映射，配置改变时要求复核 |
| 分组状态 | 按账号真实分组归属汇总模型通过、失败、待定及独立令牌数 |
| 智能选线 | 扫描所有可访问分组，识别名称与等级，折算成本，按调度分组倍率比较成本 |
| 令牌补齐 | 用户选择该模式时，为折算成本倍率低于调度分组倍率等条件的缺失线路创建令牌 |
| 持久保存 | 服务端加密文件，保留授权续期、探测开关、历史和账号关联 |

目前尚未实现“根据探针结果自动修改调度站点账号调度配置”。页面显示调度站点账号的 schedulable 状态，来自调度站点快照；本地关联保存不会改变它。

## 3. 下一步优先做什么

先完成调度站点实际账号与上游令牌的准确对应，再实现只生成建议、不写入调度站点的调度预览。不要在大批账号尚未关联的情况下，依据站点总可用率批量停用账号。

优先顺序：

1. 确认常用调度站点分组包含哪些账号。
2. 给实际使用的 API Key 账号补齐令牌与模型关联。
3. 启用这些令牌的探测，积累每个模型的实际成功、失败与超时记录。
4. 为每个分组、每个模型生成候选列表和推荐顺序。
5. 核对建议与调度站点真实请求结果后，再实施有限范围的写入控制。

验收时至少覆盖：同站不同 Key、同 Key 被多个账号复用、模型别名映射、账号配置改变、余额不足、远程目录不完整、监控数据过期。

## 4. 自动识别账号关联

建议后续利用调度站点账号的 Endpoint 和 Key 指纹与已保存上游凭据核对。密钥仅在服务端比较，浏览器接收匹配结果，不接收原始 Key。

匹配顺序建议：

| 证据 | 建议处理 |
| --- | --- |
| Endpoint 与 Key 均唯一精确匹配 | 提供可确认的高可信候选 |
| Endpoint 相同、Key 隐藏或有多个候选 | 列出候选，让管理员确认 |
| 仅名称含供应商或模型关键词 | 只作为搜索提示 |
| 协议或模型映射不一致 | 提示差异，不自动认定有效 |

一个账号可支持多个模型，同一模型可由多个独立令牌供应。数据主键应始终包含调度站点 ID、账号 ID、上游站点 ID、令牌 ID、模型和协议，不能仅按名称合并。

OAuth 等非 API Key 类型账号没有可直接对应的供应商令牌时，应明确展示未接入直测的原因，不能借用别的账号结果。

## 5. 调度建议如何生成

先判断候选资格，再比较优先级。高利润不能覆盖明确故障；历史成功率高也不能掩盖当前授权失效。

建议候选门槛：

- 分组、账号启用且允许调度。
- 账号关联已确认，调度站点快照完整且没有过期。
- 令牌有效、余额允许、模型协议受支持。
- 该令牌模型有近期有效探测结果。
- 成本已知时低于调度站点目标分组倍率。

候选排序可先使用清晰的顺序规则：近期稳定成功优先，再比较失败频率、响应耗时和折算成本。初期不必引入不易解释的总评分。

每条建议应展示：建议对象、原状态、目标状态、原因、使用的数据时间、关联版本。管理员应能追溯某次建议依据了哪把 Key 的哪一个模型。

## 6. 失败、降级和恢复

一次超时不能证明上游永久不支持该模型。应分开处理：

| 结果 | 推荐处理 |
| --- | --- |
| 短暂网络超时或 5xx | 降低优先级或短时避让，保留恢复探测 |
| 429 限流 | 在对应范围内退避，避免把限流直接当永久不可用 |
| 401、明确 Key 失效 | 检查令牌与授权，阻止受影响候选 |
| 明确不支持模型 | 排除该令牌与模型组合，保留历史和重新验证入口 |
| 返回成功状态但无有效内容 | 标为待确认，不能计为成功 |
| 监控数据过期 | 标记未知，停止基于该证据扩大自动操作 |

自动调度应有迟滞：连续异常才进行降级，恢复需连续成功观察；切换后设置最短保持时间，防止每分钟来回抖动。具体阈值应根据真实记录确定，而不是把本文建议直接当生产配置。

目前页面已有“异常折叠、成功恢复展示”，这是展示行为。调度站点账号自动恢复调度仍属于后续功能。

## 7. 模型粒度与账号粒度的区别

如果一个账号的 GPT 模型失败，但 Claude 模型正常，不应直接停掉整账号。优先针对模型做路由限制；只有账号级错误影响全部模型时才考虑账号级操作。

实际可写范围必须以所用 Sub2API 版本支持的接口和配置为准。若仅有账号启停、无法按模型限制，先给出人工建议，不模拟不存在的 API 能力。

同一 Key 被多个账号引用时，其故障会影响多个账号，但不能把这些账号当作独立备用源。分组至少应有两个真正独立的令牌或供应商，才具有相应冗余。

## 8. 成本与倍率

智能选线和自动推送统一按目标调度站分组倍率判断。上游适用倍率乘高峰因子，再除以充值倍率，得到折算成本倍率；严格低于调度分组倍率即可入选，不再设置最低毛利百分比或手工参考售价。

相等、更高或成本未知时不自动新增线路。模型基础价、长上下文、套餐和按次计费会影响实际费用；成本信息不完整时保留待确认原因。

## 9. 验证调度站点实际调用路径

上游直测成功只能说明监控服务器可以使用该 Key 与模型。建议后续增加一条经过调度站点模型入口的低频验证，以检查调度站点网络、协议、模型映射和账号配置。

此验证使用调度站点业务调用 Key，不能使用 Admin API Key。应尽可能记录命中的调度站点账号，避免请求实际走了另一个健康账号却被误认为目标账号已恢复。

在无法确定命中账号时，将结果标为分组入口验证，不能冒充某个账号的独立验证。

## 10. 有限范围自动执行

建议完成预览验证后再实施，先选一个调度站点分组作为试点：

1. 读取最新调度站点配置与本地关联版本。
2. 核对建议尚未过期，人工配置没有发生变化。
3. 只写入此次决策必要的最小字段。
4. 回读调度站点，确认目标配置生效。
5. 保存原值、目标值、原因、执行结果和恢复条件。

请求超时可能表示“写入已发生，但响应丢失”。应先回读，不能盲目重复写入。人工禁用的账号不能被自动恢复逻辑擅自重新开启。

自动控制需要一键暂停、按分组关闭以及可追溯的回滚。暂停自动控制后，既有模型探测和历史查看仍应继续工作。

## 11. 页面组织

保持现有分工：调度站点页配置连接，线路管理处理分组状态、账号关联和选线，探针监控查看令牌模型证据。默认列表每行只放身份、当前结论和关键计数；长原因、模型映射和成本公式放在详情。

未来的调度预览可以新增独立视图，展示“推荐使用、建议避让、等待确认”，不要把所有操作重新堆回调度站点分组表。

手机端保留搜索、筛选、查看详情与恢复入口，避免依赖横向滚动才能找到操作按钮。

## 12. 存储与发布

当前单服务进程与加密文件足以承载已有配置。引入多进程写入、大量决策事件或复杂查询时，再迁移数据库与事务，不必为了移除站点依赖同时重写存储层。

发布只更新代码，不携带开发机器上的账号、Key、历史或存储密钥。升级前后校验上游、调度站点及账号关联，服务异常应能回滚。

旧主站数据不参与新流程。保留历史文件用于回滚不等于继续维护或访问主站；如需永久清理存档，应另行处理备份和数据生命周期。
