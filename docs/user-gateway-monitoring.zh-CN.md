# 用户网关监控：NewAPI 主站探测与线路归因

更新：2026-09-22。本文记录新增的三层监控闭环设计与实现边界。

## 1. 为什么需要这一层

此前项目只有一条观测边：**监控站 → 上游**。用户实际走的是：

```text
用户 → NewAPI 主站（用户网关）→ Sub2API 调度站点 → 调度账号 → 上游令牌与模型
```

中间两跳完全未被验证，因此存在一类**现有探针永远发现不了**的故障：

| 故障类别 | 直连上游探针 | 本层探针 |
| --- | --- | --- |
| 上游令牌失效、余额耗尽、模型下架 | 能发现 | 也能发现（间接） |
| Sub2API 账号被冷却、并发打满、账号 error | 发现不了 | 能发现 |
| 模型映射写错、白名单漏模型 | 发现不了 | 能发现 |
| 主站侧分组/计费/协议不匹配 | 发现不了 | 能发现 |

反过来，本层探针**不能定位是哪条上游线路坏了**——它只能证明"用户这条路当前通不通"。两个问题需要两层探针分别回答。

## 2. 三层闭环

| 阶段 | 手段 | 回答的问题 | 费用 | 权限 |
| --- | --- | --- | --- | --- |
| 1 余额 | 读取上游账户余额 | 账户还有没有钱 | 免费 | 普通用户令牌（已实现） |
| 2 症状 | 用主站下游 key 探测 | 用户实际会不会成功 | 计费 | 下游 key |
| 3 归因 | 读主站管理员日志 | **哪条线路**坏了 | 免费 | **主站管理员 PAT** |

分工原则：**探针负责发现，日志负责归因。** 不用网关探针的失败去触发上游账号暂停，因为分组粒度的失败无法归因到具体令牌，那样会误伤健康线路。

### 2.1 归因为什么必须用管理员权限

`new-api/model/log.go:116` 的 `formatUserLogs()` 会清空 `ChannelName`，并把 `other` 按 `logOtherVisibilityUser` 过滤；`admin_info`（含 `use_channel` 实际尝试过的渠道 ID 顺序）对普通用户被剥离。源码注释明确要求 root 调用者不得走该格式化器。

因此第三阶段需要主站管理员 PAT（角色 ≥ 10，具备渠道读取权限），只读日志，不做任何写操作。

### 2.2 探测粒度与凭据绑定

- 主站下游 API key 绑定单个分组（Sub2API 侧同理：`api_keys.group_id`，网关鉴权读 `apiKey.GroupID`），**没有**按请求头切换分组或指定账号的能力。
- 因此覆盖多个分组需要**每个分组一把 key**。
- 一次网关探测无法指定落到哪个调度账号，**归因必须靠主站日志反查**，不能靠探针本身。

## 3. 成本与污染约束

网关探测走**真实计费路径**，按该分组倍率对 key 所属账户扣费，与直连上游探测的性质完全不同：

- 直连探针消耗上游账户额度，不产生主站账单。
- 网关探针是真实出账流量，会写进主站日志与用量统计。
- key 自身的 `rate_limit_5h/1d/7d` 与并发限制会限制探测频率；**把 key 打到限流会被误判成上游故障**。

因此默认策略：

- `GET /v1/models`（零成本）用于验证 key + 分组连通并获取该 key **真实可见**的模型目录。
- 真实模型调用按代表模型低频执行，**不默认全量同频**。
- 全量模型探测仅在手动"验证此分组"时执行。
- 探测请求带固定 `User-Agent`，便于在主站日志中识别与排除探测流量。

## 4. 数据模型

```text
user_gateways            主站连接（endpoint、管理员 PAT、状态）
user_gateway_keys        该主站的下游 key（分组绑定、探测开关、模型目录）
user_gateway_probes      「主站 × 分组 × 模型」探测结果
user_gateway_attribution 一次故障归因：时间窗、模型、命中的渠道与调度账号
```

独立 SQLite scope，与上游 `probe_history` 分开保存，互不覆盖。

## 5. 实现边界（不在本次范围）

- 不用本层探测结果自动暂停或恢复上游账号。
- 不实现主站侧分组、定价、渠道的写操作。
- 不自动完成人机验证或绕过主站校验。
- 不把探测流量伪装成业务流量。
